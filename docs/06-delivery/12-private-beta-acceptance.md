# پذیرش private beta با شاهد

بخش‌های آخر private beta چیزهایی هستند که فقط مالک می‌تواند بدهد: کلید AI واقعی، سرور واقعی، تنظیمات حساب GitHub و تصمیم دربارهٔ کاربران beta. کد نمی‌تواند این‌ها را «انجام بدهد»، ولی می‌تواند **نشان بدهد کدام‌شان هنوز مانده و کدام اثبات شده است**. این سند سه ابزار فقط‌خواندنی را معرفی می‌کند که همین کار را می‌کنند و می‌گوید خروجی‌شان را کجا بچسبانید تا Issueهای [ING-005 (#53)](https://github.com/farhaddgm/Docoo/issues/53)، [SEC-001 (#89)](https://github.com/farhaddgm/Docoo/issues/89) و [REL-002 (#94)](https://github.com/farhaddgm/Docoo/issues/94) با شاهد بسته شوند، نه با «فکر می‌کنم درست است».

## ۱. سه ابزار

| ابزار                                 | کجا اجرا می‌شود                       | چه چیزی را نشان می‌دهد                                                                                                                                                                                              | Issue |
| ------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| `pnpm owner:check`                    | رایانهٔ شما (کلید GitHub فقط‌خواندنی) | حفاظت شاخهٔ `main`، CodeQL، اینکه Actions اصلاً job را شروع می‌کند، کدام کلیدهای پذیرش تنظیم شده‌اند و آخرین اجرای «Provider acceptance»                                                                            | #89   |
| گردش‌کار **Provider acceptance**      | GitHub Actions (با secretهای مخزن)    | قرارداد ساختاریافتهٔ هر provider با کلید واقعی، **خروجی پنج مرحله و ارزیابی نقش‌های Brain با schema خود Docoo**، و تبدیل گفتار به متن روی corpus پذیرش. هر بخش بدون کلیدش «رد می‌شود» و در خلاصهٔ اجرا نوشته می‌شود | #53   |
| `sudo ./scripts/deploy/acceptance.sh` | روی سرور production                   | سلامت کانتینرها، آماده‌بودن API، HTTPS و روزهای باقی‌ماندهٔ گواهی، فضای دیسک، نسخهٔ در حال اجرا در برابر آخرین Release، به‌روزرسانی شبانه، پشتیبان خارج از سرور، ادمین فعال، اتصال AI واقعی و سالم و تنظیم ایمیل    | #94   |

هر سه فقط می‌خوانند؛ چیزی را عوض نمی‌کنند، کلیدی چاپ نمی‌کنند و هیچ‌جا چیزی نمی‌فرستند (فقط `owner:check` با API گیت‌هاب حرف می‌زند).

### وضعیت‌ها

| وضعیت     | معنی                                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------------- |
| `PASS`    | شاهد دیده شد                                                                                          |
| `WARN`    | کار می‌کند ولی چیزی نزدیک مشکل است (نسخهٔ عقب‌تر، گواهی نزدیک انقضا، تایمر خاموش)                     |
| `ACTION`  | فقط مالک می‌تواند انجامش بدهد؛ همان خط می‌گوید کجا و چه کار کند                                       |
| `FAIL`    | خراب است. `acceptance.sh` در این حالت با کد ۱ بیرون می‌آید                                            |
| `UNKNOWN` | این ابزار با دسترسی فعلی چیزی ندید (کلید GitHub دسترسی admin ندارد، یا اسکریپت با sudo اجرا نشده است) |

## ۲. ترتیب پیشنهادی برای مالک

1. **GitHub.** یک token فقط‌خواندنی برای همین مخزن بسازید (classic با دسترسی `repo`، یا Fine-grained با خواندن Administration، Actions، Secrets و Code scanning) یا روی رایانه‌ای که `gh` دارد یک‌بار `gh auth login` بزنید، و در پوشهٔ مخزن اجرا کنید. نام مخزن از `git remote` خوانده می‌شود:

   ```bash
   GITHUB_TOKEN=<token> pnpm owner:check            # فارسی
   GITHUB_TOKEN=<token> pnpm owner:check --lang en
   ```

   چیزی که token نبیند `UNKNOWN` نوشته می‌شود، نه موفق. فقط `FAIL` کد خروج ۱ می‌دهد؛ `ACTION` کار شماست و خطا نیست.

   هر خط `ACTION` همان گام را می‌گوید (حفاظت شاخه، روشن‌کردن CodeQL، ثبت secret). اگر خط «اجرای Actions» می‌گوید jobها در ثانیهٔ اول بدون گام شکست می‌خورند، مشکل سقف هزینه یا اعتبار GitHub است نه کد؛ تا حل نشود هیچ گیت CI چیزی را اثبات نمی‌کند.

2. **کلیدهای پذیرش.** در Settings → Secrets and variables → Actions این secretها را بسازید: `OPENAI_API_KEY`، `GEMINI_API_KEY`، `ANTHROPIC_API_KEY` و `TRANSCRIPTION_API_KEY`. هر مورد که ندارید فقط همان بخش را رد می‌کند. اگر نام مدل خاصی می‌خواهید، متغیر `<PROVIDER>_MODEL` را بگذارید؛ وگرنه اولین مدل زندهٔ فهرست provider که خروجی ساختاریافته می‌دهد انتخاب می‌شود (نام مدل در کد ثابت نیست). سپس Actions → **Provider acceptance** → Run workflow. خلاصهٔ اجرا فهرست «تنظیم‌شده، آزموده شد» و «تنظیم نشده، رد شد» است؛ همان را در #53 بچسبانید.

3. **سرور.** پس از نصب ([راهنمای نصب](11-production-install.md)) و ورود کلید AI در صفحهٔ «ارائه‌دهندگان AI» (و زدن «بررسی سلامت»):

   ```bash
   sudo ./scripts/deploy/acceptance.sh | tee ~/acceptance-$(date +%F).md
   ```

   جدول را در #94 بچسبانید. اگر بخواهید همان ماشین قبل از beta چند روز بماند، این را هفته‌ای یک بار دوباره بگیرید؛ تغییر وضعیت‌ها همان چیزی است که باید دیده شود.

4. **امضا.** وقتی هیچ `FAIL` و `ACTION`ی که برای شما مهم است نمانده و فهرست «فقط مالک می‌تواند تأیید کند» در انتهای گزارش سرور علامت خورده، بلوک «Sign-off» همان گزارش را با تاریخ در #94 بگذارید. [طرح پذیرش](05-acceptance-and-traceability.md) می‌گوید امضا باید نسخهٔ مستندات، commit، digest image و محدودیت‌های شناخته‌شده را هم داشته باشد؛ همه از همان گزارش و Release قابل برداشت‌اند.

## ۳. چه چیزی را این ابزارها **گواهی نمی‌کنند**

- **کیفیت متن مدل.** پذیرش provider یعنی: پاسخ با schemaهای خود Docoo، در حالت ساختاریافتهٔ همان provider، برگشت و کلیدهای الزامی را داشت؛ ارزیابی Brain از قرارداد «شاهد یا حذف» گذشت. اینکه مدل نقل‌قول‌های تحقیق را عین متن آورد در لاگ اجرا چاپ می‌شود ولی معیار قبولی نیست. این نمی‌گوید راه‌حل‌ها خوب‌اند. کیفیت را ادمین در پایلوت واقعی می‌سنجد.
- **سازگاری schema با provider بعدی.** آزمون ثابت `schema-compat` هر schema پلتفرم را با باریک‌ترین قاعدهٔ شناخته‌شده (OpenAI strict) می‌سنجد، ولی فقط پذیرش زندهٔ بالا می‌گوید provider امروز همان را قبول دارد. به همین دلیل این گردش‌کار هفته‌ای یک بار و با تغییر آن فایل‌ها اجرا می‌شود.
- **بازیابی پشتیبان روی ماشین دیگر.** `acceptance.sh` فقط وجود base backup خارج از سرور را می‌بیند. تمرین restore با [runbook](10-runbooks.md) بخش ۸ را خودتان یک بار انجام دهید و تیک بزنید.
- **تصمیم‌های انسانی.** کاربران beta، کانال گزارش مشکل و پذیرش نهایی.

## ۵. نگه‌داری

- هر judgement در `acceptance.sh` یک تابع خالص است و با `bash scripts/deploy/acceptance.test.sh` (در CI با `pnpm deploy:test`) با ورودی‌های ساختگی آزموده می‌شود؛ جمع‌آوری از Docker و PostgreSQL در Deploy smoke روی نصب واقعی آزموده می‌شود.
- افزودن secret یا provider جدید: `ACCEPTANCE_SECRETS` در `scripts/owner/check-github.mjs` و فهرست `env` و گام‌های گردش‌کار Provider acceptance را با هم تغییر دهید (آزمون `check-github.test.mjs` فقط رفتار خود اسکریپت را می‌سنجد، نه هم‌خوانی با فایل گردش‌کار).
- این سند هیچ وضعیت «تمام شد»ی را از طرف مالک ادعا نمی‌کند. تا وقتی امضا در #94 نیست، private beta **آمادهٔ پذیرش** است، نه پذیرفته‌شده.
