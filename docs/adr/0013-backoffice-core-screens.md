# ADR-0013: صفحه‌های اصلی بک‌آفیس — حوزه، پروژه، گردش‌کار، راه‌حل و سند

## زمینه

پس از فاز ۶ همهٔ قابلیت‌های هستهٔ محصول در API بودند، ولی بک‌آفیس فقط داشبورد، ارائه‌دهندگان AI، Audit Log، هزینه و گزارش Brain را داشت ([ADR-0011](0011-reporting-and-brain-reports.md): «ایجاد پروژه و حوزه هنوز UI ندارد»). مالک غیرفنی نمی‌توانست پروژه بسازد، گردش‌کار را تأیید یا رد کند، راه‌حل انتخاب کند یا سند را تأیید و دریافت کند؛ gate فاز ۵ («پذیرش ادمین بدون ابزار توسعه») بدون این صفحه‌ها بسته‌شدنی نیست.

## تصمیم

- **صفحه‌ها:** حوزه‌ها (`/topics`: فهرست با نما، ساخت، ویرایش نسخه‌دار، بایگانی، بازیابی، حذف)، پروژه‌ها (`/projects`، `/projects/new`) و صفحهٔ پروژه (`/projects/{id}`) با بخش‌های نمای کلی، گردش‌کار، راه‌حل‌ها، اسناد و تاریخچه. بخش فعال در `?tab=` می‌ماند و تعویض زبان آن را حفظ می‌کند (hash عمداً نه).
- **ساختار کد:** صفحه‌ها client component روی همان API هم‌مبدأ هستند (مثل صفحهٔ ارائه‌دهندگان). `WorkspacePage` نشست و workspace را می‌گیرد، `useAction` همزمانی یک اقدام را تضمین می‌کند و نتیجه را در `Notice` اعلام می‌کند (`status` برای موفقیت، `alert` برای خطا، با scroll به دید). متن هر صفحه در ماژول `messages` دوزبانه است و خطا از روی `code` مسئله به پیام محلی تبدیل می‌شود؛ `ApiError` فهرست `problems` را هم نگه می‌دارد تا «چرا پروژه آماده نیست» نشان داده شود.
- **چرخهٔ عمر سمت‌سرور:** پاسخ پروژه `availableCommands` دارد که از `@docoo/domain` (همان ماشین حالت) ساخته می‌شود و پس از پایان مهلت ۳۰روزه `restore` را حذف می‌کند. UI دقیقاً همین دکمه‌ها را نشان می‌دهد و قاعده را تکرار نمی‌کند.
- **اقدام حساس:** `pause`، `complete` و `reopen` دلیل لازم دارند و `archive` و `delete` ابتدا اثر خود را نشان می‌دهند؛ هر دو در پنل درجا (نه modal) با انتقال focus به عنوان پنل. حوزه‌ای که پروژه به آن وابسته است پیش از بایگانی/حذف، پروژه‌های وابسته را فهرست می‌کند.
- **همزمانی خوش‌بینانه:** ویرایش `If-Match` با نسخهٔ بارگذاری‌شده و فرمان‌ها `expectedVersion` می‌فرستند؛ تعارض به‌صورت پیام «صفحه را به‌روز کنید» دیده می‌شود.
- **بازبینی گردش‌کار:** خروجی هر مرحله بر اساس schema همان مرحله خوانا نمایش داده می‌شود و هر چه مطابق نباشد به JSON برمی‌گردد. تأیید، رد (با بازخورد)، نظر و ویرایش (نسخهٔ جدید JSON) و تصمیم سقف attempt هر کدام `Idempotency-Key` تازه می‌فرستند. پنل گردش‌کار تا زنده‌بودن اجرا وضعیت را می‌خواند (هر ۵ ثانیه وقتی مرحله‌ای در حال اجراست، هر ۱۵ ثانیه وقتی منتظر شما یا متوقف است، و فقط وقتی تب دیده می‌شود) و اعلان نتیجه را خودش نگه می‌دارد تا با بسته‌شدن پنل بازبینی گم نشود. وضعیت مرحله برای فناوری‌های کمکی در یک `status` پنهان اعلام می‌شود.
- **راه‌حل و سند:** تولید راه‌حل، ویرایش وزن معیارها (جمع ۱۰۰، با دلیل)، انتخاب با اولویت؛ سند با وضعیت، شمار رسمی و بازه، ارسال، ارزیابی، تأیید یا رد، پذیرش با استثنا (نشان همیشه دیده می‌شود)، قفل و بازگشایی، ساخت DOCX/PDF/PPTX با دانلود، نسخه‌ها، diff و بازیابی. متن سند در UI فقط‌خواندنی است.
- **آزمون:** `core-flow.spec.ts` روی API واقعی، Temporal و worker ایجنت (ارائه‌دهندهٔ fake) کل مسیر را با کیبورد و axe می‌پیماید؛ Playwright خود worker را بالا می‌آورد (آمادگی از پورت متریک آن). متن‌های آزمون از همان ماژول‌های messages می‌آیند.

## پیامدها

- ویرایش بلوک‌های سند و نگارش کامل سند توسط عامل documentation، ایجنت‌ها و قالب‌ها (پرسش‌وپاسخ تحلیلگر در [ADR-0014](0014-analyst-questions-and-answers.md) آمد)، دانش و ممیزی (بارگذاری منبع، صف ممیزی، override) و تنظیمات سامانه هنوز UI ندارند؛ ناوبری آن‌ها «به‌زودی» می‌ماند ([نقشهٔ راه](../06-delivery/04-roadmap.md)).
- خواندن‌ها یک بار بعد از خطای شبکه یا gateway تکرار می‌شوند، ولی فرمان‌ها هرگز خودکار تکرار نمی‌شوند؛ پاسخ `AUTH_RATE_LIMITED` (سقف ۱۲۰ درخواست در دقیقه برای هر نشانی) پیام محلی دارد و آزمون E2E که همهٔ درخواست‌ها را از یک نشانی می‌فرستد با `API_RATE_LIMIT_PER_MINUTE` بالاتر اجرا می‌شود.
- polling برای beta کافی است؛ اگر تعداد پروژه‌های هم‌زمان بالا رفت باید به رویداد سمت‌سرور (SSE) برود.
- ساخت PDF و دانلود به Chromium و ذخیره‌گاه فایل روی سرور نیاز دارد؛ نبود آن‌ها به‌صورت پیام صریح دیده می‌شود.

## رد گزینه‌ها

modal برای اقدام حساس ([UX](../01-product/05-backoffice-ux.md) §۱۳)، تکرار قواعد وضعیت در مرورگر، fetch سمت‌سرور با کوکی نشست، و WebSocket/SSE برای وضعیت گردش‌کار در این مرحله رد شدند.
